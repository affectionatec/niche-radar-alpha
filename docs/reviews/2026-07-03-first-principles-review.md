## 1. 结论（TL;DR）

**工程质量：8/10（真实、可复现）。产品验证：2/10（几乎为零）。**

这个项目的工程纪律远超同阶段的 alpha 项目：481 个测试真实全过、架构分层清晰、容错设计经过实测。但从第一性原理看，它有一个致命的倒置——

**产品的全部价值 = 榜单质量（操作者最终看到的 10 个 niche 是否值得做）。**
采集器数量、agent 数量、文档数量都只是手段。而恰恰是"榜单质量"这一项，整个项目至今**没有任何测量**：

- 所谓"评估门"在本次评审前是一个恒真式（见 §3-F1），从未执行过任何 agent 代码；
- 仓库里不存在一份真实管线跑出来的报告（样例报告是手写的）；
- 最近 7 个 PR（M1–M4 全部工作量）都投在"加采集器"上，把源从 16 个扩到 23 个，却没有一次端到端的真实运行验证。

**一句话诊断：这是一台造得很精良、但从未真正点过火的发动机。下一阶段的全部资源应该从"加进气管"转向"点火并测推力"。**

## 3. 关键发现

### F1 — 评估门是恒真式【最严重；本 PR 已修复】

CI 强制执行的 `python -m niche_radar.eval.runner`，修复前的实际逻辑：

```python
results[item.item_id] = {"a1_pass": fixture.is_valid_signal}   # 读 fixture 文件 A
summary = evaluate_against_golden(items, results)              # 对比 golden 文件 B
```

**两个 JSON 文件互相对答案，A1 agent 的代码一行都没执行过。** `MockLLMClient` 实现的接口（`chat_completion` 返回字符串）与真实管线的接口（`complete_structured` 返回 dict）根本不兼容——它是从未接线的死代码。verdict/tier/score 三类检查准确率 0%，但退出码规则只看 A1，所以 CI 永远绿。

黄金集只有 5 条样本。

**修复的证明**：改造后评估门第一次运行就抓到一个真实 bug——`golden_004` 的 fixture 用了非法枚举值 `signal_type: "complaint"`（合法值是 `pain_point/feature_request/competitor_complaint/noise`），旧门下它静默通过了不知多少次 CI。

本 PR 的落地（详见 §6）：MockLLMClient 重写为真实 `LLMClient` 协议；runner 现在把每条黄金样本送进真实的 `orchestrator.run_single`（A1→A2 链），实际执行 prompt 构建、Pydantic 校验、短路判定；agent 硬失败不再伪装成"拒绝"；未接线的 verdict/tier/score 检查显式标注为"未评估"而非静默忽略。

### F2 — 投入方向倒置：广度 > 验证【需要用户决策】

M1–M4 共 9 个任务、7 个 PR、110 个新测试，全部投在**输入侧**（新采集器/新后端）。同期**输出侧**（管线到底产出什么质量的榜单）的投入为零。

从第一性原理算一笔账：

- 23 个源 × 未知的信号质量 = 未知的榜单质量。
- 新增 7 个源中 3 个（小红书、LinkedIn、小宇宙）默认关闭（Jina opt-in），默认配置下**贡献为零**；其余多为"guest-cookie 反爬"类，是维护负债最重的一类。
- 没有任何数据回答"哪个源贡献了高分 niche"——连砍掉低产出源的依据都不存在。

**边际收益最高的下一步不是第 24 个源，而是第 1 次被测量的真实运行。**

### F3 — 481 个测试全是 mock，爬虫腐烂不可见【本 PR 部分缓解】

测试套件对回归很好，但所有网络和 LLM 都被 mock。平台改版 HTML/API 后，源会静默归零而 CI 依然全绿——这正是爬虫类项目最常见的死法。

本 PR 落地：`niche_radar/eval/canary.py` + 每周一次的 `canary.yml` workflow，用无钥匙采集器直接打真实网络，按源报告产出量，多数源归零则告警。刻意不做 PR 门禁（真实端点允许抖动）。

### F4 — 文档链自重超载 + 已经漂移【本 PR 已清理】

六文档链 + 独立验证人 + 交接日志，对单人 alpha 项目是重资产流程。它产出了漂亮的文档，但也产出了漂移：README/AGENTS 说 16 个平台（实际 23）、status.md 落后于 git 事实、约 200KB 的四棵遗留文档树（`.ralph/`、`docs/superpowers/`、`PRODUCT.md`、旧增强/集成计划）与"单一事实来源"的宣称直接矛盾。用户的直觉（"过去的记忆已经老旧"）是对的。

本 PR 落地：删除全部遗留树（git 历史可恢复）；修正所有计数漂移；刷新 status.md。
**进一步建议（未动，需用户拍板）**：把六文档链收缩为三件——`AGENTS.md`（怎么干活）+ `status.md`（干到哪了）+ `adr/`（为什么这么定）。PRD/SPEC/PLAN 合并进 ADR 与代码注释。单人项目的文档应该为"下一次会话的上下文恢复"服务，而不是为流程本身服务。

### F5 — 样例报告冒充管线输出【本 PR 已修正措辞】

`docs/sample-reports/*.md` 头部自称 "Generated by the 8-agent pipeline"，实为手写示例。对一个以"可信度"为卖点的分析工具，这种小失真是最不该有的。已改为如实标注 "Hand-written illustration"。**根治方法是 §5-P0：跑一次真的，把真实报告放进来。**

## 4. 从第一性原理重新推导

**这个产品存在的唯一理由**：操作者早上打开 dashboard，看到的 top-10 里至少有 1 个让他觉得"这个值得深挖"。做不到这一点，其他一切都是零；做到了，哪怕只有 5 个源也是好产品。

由此反推优先级：

1. **信号质量 > 信号数量。** HN + Reddit + Indie Hackers 三个高浓度源的信噪比，可能超过 23 个源的大杂烩。垃圾进 → LLM 加工 → 精致的垃圾出。
2. **测量是改进的前提。** A1 的过滤准确率、A6 verdict 的合理率、聚类的纯度——每一环都可以被黄金集测量，但目前黄金集只有 5 条、且只覆盖 A1。
3. **反馈回路是护城河。** 操作者每天标记"这条推荐好/差"，数据回流黄金集 → prompt 调优有了地面真值。这是这类产品从"玩具"到"工具"的分水岭，目前完全缺失（shortlist 只有收藏功能）。
4. **爬虫是消耗品，不是资产。** 每个源都会腐烂，维护成本永续。源的数量应该由"单源贡献度数据"决定增减，而不是由路线图决定只增不减。

## 5. 建议路线图（按优先级）

### P0 — 点火：第一次被测量的真实运行（1–2 天）
用一个便宜的 LLM key（DeepSeek/Groq），在真实网络上完整跑一轮 collect → analyze → report。把真实报告（连同成本数字：多少 items、多少 clusters、多少 LLM 调用、几块钱）作为 artifact 存进 `docs/sample-reports/`，替换手写示例。**这是当前信息量最大的单一行动**——它会立刻暴露真实的信噪比、聚类质量和提示词问题。

### P0 — 把黄金集从 5 条扩到 50+ 条（与上一条联动）
从真实运行的 raw_items 里人工标注 50 条（A1 应过/应拒）。用真实数据校准 A1，才谈得上信噪比。顺手把 cluster 阶段（A3–A8）的 fixture 回放接进评估门，让 verdict/tier/score 检查从"未评估"变成真检查。

### P1 — 反馈回路（2–3 天）
Shortlist 页加"准确/不准确"两键反馈，落库。每周把反馈导出为黄金集增量。这是数据飞轮的第一圈。

### P1 — 源贡献度看板（1 天）
现有 cost attribution 已按 agent 统计；补一个按 source 的统计：raw_items → 通过 A1 → 进入高分 niche 的转化漏斗。跑一个月，用数据砍掉零贡献源。

### P2 — 流程减负（半天，需用户拍板）
六文档链 → AGENTS.md + status.md + adr/ 三件套（见 F4）。

### 冻结项
在 P0 两项完成前：**不加新采集器、不加新 LLM provider、不做 UI 扩展。**
